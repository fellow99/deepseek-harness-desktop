> 文档编号：000
> 状态：草案（待审阅）

## 1. 项目概述

- **工程名**：`deepseek-harness-desktop`
- **产品名**：DeepSeek Harness Desktop
- **一句话定位**：基于 Electron 的 deepseek-harness 桌面封装——主进程内跑 dsh Host（含 webserver），渲染进程同源加载 localhost，界面完全沿用 dsh 标准前端，桌面壳只补托盘、通知、无边框窗口、剪贴板等能力，让 agent harness 像一个真正的桌面应用那样运行。

## 2. 背景

- deepseek-harness（`dsh`）是 DeepSeek AI 开源的 agent harness，采用「一切皆插件」架构，由 [Cordis](https://github.com/cordiverse/cordis) 驱动，当前处于**开发者预览**阶段（`0.1.0-rc.5`），**存在破坏兼容性变更**。
- `dsh` 的原生入口是 `dsh web`（浏览器 Web UI，默认 `http://127.0.0.1:3080`）与 `dsh --profile headless`（无 UI 一次性运行）。
- `dsh` 已完成 **Host/Client 分层**：Host（Node.js）挂 `apiProxy`（RPC 网关）+ `webserver`（HTTP 载体）；Client（浏览器）通过 `dsh-client-connection` 的 `WebApiClient` 走 HTTP 上行 + WebSocket 下行。
- **关键事实**：dsh 的 webserver **同时服务 SPA dist 和 `/api`**。因此渲染进程直接加载 `http://127.0.0.1:<port>/` 就是**同源**，fetch `/api` 与 WebSocket `/api/events.mux` 都无需 CORS、无需鉴权。

## 3. 目标与原则

**目标**：

- 为 `dsh` 提供一个**一等公民**的桌面应用，而非「包一层 `dsh web` 指向 localhost」的粗壳。
- 100% 复用 `dsh` 现有 Web UI，不 fork UI。

**原则**：

1. **零上游改动**：复用 dsh 现有 HTTP 载体（`WebApiClient` + webserver 路由），**不新写 IPC 载体**。
2. **进程内 Host**：MVP 阶段 Host + webserver 跑在主进程（简化通知/托盘的 ctx 直连），进程边界设计成可迁移到 `utilityProcess`/子进程。
3. **只写装配代码**：复用 `runProfile` / `boot` / 现有插件机制，桌面能力以 host 插件或启动代码注入。

## 4. 目标平台与分发

- **平台**：Windows + Linux（macOS 后续再考虑）。
- **分发（现阶段）**：先本地打包自用（Electron Forge `make`），暂不做自动更新、代码签名、商店分发。

## 5. MVP 功能范围

**v1 必做**：

- 系统托盘 + 后台驻留
- 原生通知
- 无边框窗口 / 自绘标题栏
- 剪贴板图片粘贴

**暂缓**：全局快捷键唤起、开机自启、多窗口。

**不做（沿用 dsh 标准前端）**：原生文件/目录选择器——直接使用 dsh Web UI 内置的目录浏览（`host.listDirectory` browse 后端）。

## 6. 参考实现分析

### 6.1 opencode desktop（参考子工程 `packages/desktop/`）

opencode 的桌面壳与本项目需求高度同构（用 Electron 包装 agent harness）。其关键决策及对我们的映射见下表：

| opencode 的决策 | 对我们的取舍 |
|---|---|
| 后端跑在 `utilityProcess`（崩溃隔离） | **MVP 暂不采用**，进程内跑 Host；预留迁移点（渲染进程只认 localhost，迁移透明） |
| UI 用自定义协议 `oc://renderer` 加载 | **不采用**。opencode 的 UI 与数据 server 分离才需要；dsh 的 webserver 同源服务 dist + `/api` |
| Basic auth + CORS 头注入 | **不采用**。opencode 因 `oc://` 跨源才要；我们同源加载 localhost |
| 动态端口 + 两级就绪 + `awaitInitialization` IPC 门 | **采用（简化）**。`--port 0` + 读 `ctx.webServer.port` + 就绪后 `loadURL` |
| 薄 IPC（窗口/对话框/store/更新/深链），数据面不过 IPC | **采用** |
| `sandbox:true` + `contextIsolation:true` + `nodeIntegration:false` | **采用** |
| 强制 loopback 进 NO_PROXY + 系统 CA + 代理 | **采用** |
| 无边框 + `titleBarOverlay`（win32） | **采用** |
| 导航加固 + 权限白名单（clipboard-sanitized-write + notifications） | **采用** |
| 单实例锁 | **采用** |
| 构建：electron-vite + electron-builder | **分歧点**（见开放问题 3；本 brief 原定 Electron Forge） |

**关键差异总结**：opencode 因「UI 与数据 server 分离」被迫上了 `oc://` 协议 + Basic auth + CORS 三件套；本项目同源加载 localhost，三样全省，比 opencode 更简。

### 6.2 dsh 架构与插件机制（决定性的架构事实）

- `dsh` 的 webserver（`@deepseek-ai/dsh-host-webserver`）同时服务 SPA dist（fallback 席位）与各插件注册的 `/api` 路由；`dsh-client-connection` 的 node half 把 `/api` 桥 + WebSocket 下行注册到 webserver 上。
- `dsh-client-connection` 的 client half（`WebApiClient extends AbstractApiClient`）已实现 HTTP 上行 + WebSocket 下行，**无需改动即可复用**。
- **插件机制完善**：
  - **后端（host）**：Cordis「一切皆插件」，`ctx.plugin()` 注册服务/工具/路由，profile 的 `cordis.patch.yml` 挂树外插件。
  - **前端（client）**：`dsh.client` 机制（声明 `dsh.client` + 打 client bundle + 进组合 + host 服务 `/plugins/<id>/client.js`）。
  - 结论：桌面能力优先以**后端插件/启动代码**注入（托盘、通知），前端注入留作后续往 dsh UI 加新功能时用。

## 7. 架构方案（选定：进程内 Host + webserver + localhost 同源数据面）

**核心**：Electron 主进程内 `runProfile('desktop')` 挂起 Host（含 webserver，绑定 `127.0.0.1:<空闲端口>`）；渲染进程 `loadURL('http://127.0.0.1:<port>/')` 同源加载 dsh Web UI。

**为什么放弃「零 webserver + IPC」的原方案 A**：

- `dsh-client-connection` 的 node half 硬依赖 `webServer`（`inject: ['webServer']`，在它上面注册 `/api` 路由与 WebSocket 下行）。
- 其 client half 硬编码 `new WebApiClient()`，无 IPC 注入点。
- 即「IPC 桥子类」在 dsh 中是文档原话「假想示例——尚无此形态」，要落地必须**新写 node + client 两个 half 的载体插件**——这是上游改动，不是「零改」。

**为什么进程内而非子进程**：

- 进程内直连 `ctx`，通知/托盘订阅 `session/event` 最省事。
- 渲染进程只认 `http://127.0.0.1:port`，将来迁 `utilityProcess`/子进程对渲染进程透明，迁移成本极低。

**与 opencode 的差异**：

| | 本项目 | opencode |
|---|---|---|
| UI 加载 | `loadURL(localhost)` 同源 | `oc://` 自定义协议 |
| 鉴权/CORS | 无 | Basic auth + CORS 注入 |
| 后端进程 | 主进程内（MVP） | `utilityProcess` |
| 数据面 | HTTP + WebSocket（同源） | HTTP + WebSocket |

## 8. 消费方式（选定：选项 2 本地源码引用，同级目录非 submodule）

- **目录约定**：`deepseek-harness` 与本工程放在**同级目录**（非 git submodule），引用路径 `../deepseek-harness`。
- **理由**：`@deepseek-ai/dsh`（apps/cli）只暴露 `bin`（无 `main`/`exports`），`runProfile` 只能从源码 import（`apps/cli/src/profile-boot.ts`）。源码引用能直接 import 任意 host/client 包、能自建前端 dist、能紧跟上游快速迭代。
- **构建**：桌面工程的 build 流水线需先对 `../deepseek-harness` 执行 `pnpm install` + `build:lib:host` + `build:lib:client` + `build:web`，再把产物与 profile 打进 resources。

## 9. 进程模型

```
┌─ Electron 主进程（Node.js，也承载 dsh Host）─────────────────┐
│  runProfile('desktop', args:['--port','0']) → { ctx, shutdown }│
│    ├─ webserver      ← 绑定 127.0.0.1:<空闲端口>，服务 dist + /api│
│    ├─ apiProxy       ← RPC 网关（createApiProxy）             │
│    └─ connection node half ← 已把 /api + WebSocket 注册到 webserver│
│  就绪后：BrowserWindow.loadURL(`http://127.0.0.1:${ctx.webServer.port}/`)│
│  ┌─ Tray / Notification：订阅 ctx 的 session/event            │
│  └─ 无边框窗口控制：ipcMain.handle(min/max/close)             │
└──────────────▲───────────────────────────────────────────────┘
               │ contextBridge：window.dsh（仅窗口控制等薄 IPC） │
┌──────────────┴───────────────────────────────────────────────┐
│ 渲染进程：loadURL('http://127.0.0.1:<port>/')  ← 同源          │
│   标准 dsh Web UI（WebApiClient：fetch /api + WS /api/events.mux）│
└──────────────────────────────────────────────────────────────┘
```

## 10. 数据流

- **上行（unary）**：渲染进程 `WebApiClient.doFetch` → `fetch('/api/<method>')`（同源，无 CORS）→ webserver 的 `/api` 路由（connection node half 注册）→ `toFetchHandler(apiProxy).fetch`。
- **下行（事件帧）**：渲染进程 `WebApiClient.openMux/openHost` → `WebSocket('/api/events.mux')` / `('/api/events.host')`（同源）→ 帧流。
- **桌面侧通知/托盘**：主进程**直接订阅 `ctx` 的 `session/event`**（进程内，无需经过 HTTP/WebSocket），触发 Electron `Notification` / `Tray`。
- **剪贴板图片**：渲染进程粘贴 → 走 dsh 图片附件路径（`session.prompt` 的 attachment）。

> 备注：原「IPC 桥子类」方案（`IpcApiClient extends AbstractApiClient`）作为**备选**保留——若将来有「必须 file:// 加载 + 零端口」的需求，再回到该路径。`AbstractApiClient` / `toFetchHandler` 的源码核实见附录。

## 11. 自定义 profile（A1）

方案需要「web 组合，微调为桌面」：

- **A1：新建 `desktop` profile**，`dsh.profile.bundles = [dsh-base, dsh-web-app]`，再用 `cordis.patch.yml` 覆盖：`web-runtime` 行 `printUrl: false`（不打印 URL 行）、webserver 行端口由启动代码注入（`--port 0`）。干净、可演进。**（推荐）**
- **A2：直接复用 `web` profile**，启动时传 `--port 0` + `--patch` 关掉 URL 打印。最省事，但依赖 web profile 内部行 id 稳定。

## 13. 四个 MVP 桌面能力 → 落地映射

| 能力 | 落地方式 |
|---|---|
| 系统托盘 + 后台驻留 | 主进程 `Tray`；关窗 = 隐藏到托盘；`window-all-closed` 不退出 |
| 原生通知 | 主进程订阅 `ctx` 的 `session/event`（`approval/requested`、`question/requested`、turn 完成）→ Electron `Notification` |
| 无边框窗口/自绘标题栏 | `BrowserWindow({ frame:false, titleBarOverlay })`（win32）；窗口控制（min/max/close）走薄 IPC；与 dsh web UI 视觉一体 |
| 剪贴板图片粘贴 | 渲染进程粘贴 → dsh 图片附件路径（`session.prompt` 的 attachment）；权限白名单放行 `clipboard-sanitized-write` |

## 14. 构建/打包 · 生命周期 · 错误处理 · 测试

- **构建打包**：
  - 先对 `../deepseek-harness` 执行 `pnpm install` + `build:lib:host` + `build:lib:client` + `build:web`（产出 host/client lib 与 `apps/web` dist）。
  - Electron Forge：makers Windows `maker-squirrel`（或 NSIS）+ Linux `maker-deb`/`maker-rpm`（或 AppImage）；把 dsh 构建产物 + dist + profile 打进 `resources/`。
  - **原生模块 ABI（已确认）**：MVP 阶段**裁掉** dsh 的 `native/landlock-run`（Linux 沙箱原生模块），规避 Electron Node ABI 不一致问题。代价：Linux 上 agent 命令无 OS 级进程隔离；后续需要沙箱时再 `electron-rebuild` 恢复。
- **生命周期**：
  - 启动：单实例锁 → `runProfile('desktop')`（`--port 0`）→ 读 `ctx.webServer.port` → 就绪 → 建窗 `loadURL(localhost)`。
  - 关闭：关窗 → 隐藏托盘；真正退出 → `shutdown.shutdown()` dispose 插件树 → `app.quit()`。
  - 崩溃：harness 在主进程 = 应用崩溃（已知代价），加 `uncaughtException`/`unhandledRejection` 兜底 + 用户提示，`host.ts` 边界预留 utilityProcess 迁移点。
- **错误处理**：业务错误走 dsh 的 `RpcError`（`RpcResult.error` 分支）；webserver 监听失败（EADDRINUSE）由 boot 大声失败上报。
- **测试**：单元——host 启动 + `toFetchHandler` 冒烟；集成——`runProfile` + 就绪判定；e2e——后续可选。

## 附录：关键接口源码核实（2026-08-14）

对载体相关 API 做了源码级核实（`packages/host/apiproxy/src/`、`packages/client/connection/src/`）：

1. **`AbstractApiClient`**（`fetch/client.ts:244`）：`export abstract class AbstractApiClient implements IApiClient`，唯一抽象方法 `doFetch(input: URL, init?): Promise<Response>`。基类持有全部协议不变量（rpcId mint、四象限信封、zod 校验、SSE 帧解码、微任务合批观测）。
2. **`toFetchHandler`**（`fetch/handler.ts:243`）：`toFetchHandler(api: ApiProxy): { fetch }`，把 `ctx.apiProxy` 变成纯 `Request → Response` 函数，自带 SSE 下行 codec（`/api/events.mux`、`/api/events.host`、unary、respond、session.export）。
3. **`WebApiClient`**（`client/web-api-client.ts:13`）：`extends AbstractApiClient`，`doFetch = globalThis.fetch`，override `openMux/openHost` 走 WebSocket——**现有浏览器载体，本方案直接复用**。
4. **connection node half**（`src/index.ts:47`）：`inject: ['webServer']`，`apply` 里 `ctx.webServer.register('/api' 路由)` + `registerUpgrade`（WebSocket）——即「零 webserver」需新写载体插件的原因。
5. **connection client half**（`src/client/index.ts:88`）：`const api = fixtureClient ?? new WebApiClient()`——无 IPC 注入点，佐证「IPC 桥子类是假想形态」。

> 结论：本方案复用 `WebApiClient` + webserver 路由，**零上游改动**；附录 4、5 解释了为何原「零 webserver + IPC」方案被放弃。
