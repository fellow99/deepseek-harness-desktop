# DeepSeek Harness Desktop — 产品概念设计

> 文档编号：000

## 1. 项目概述

- **工程名**：`deepseek-harness-desktop`
- **产品名**：DeepSeek Harness Desktop
- **一句话定位**：基于 Electron 的 deepseek-harness 桌面封装，提供深度桌面集成体验——把 `dsh` 的 Web UI 装进原生桌面壳，补齐托盘、通知、原生文件选择、多窗口等桌面能力，让 agent harness 像一个真正的桌面应用那样运行。

## 2. 背景

- deepseek-harness（`dsh`）是 DeepSeek AI 开源的 agent harness，采用「一切皆插件」架构，由 [Cordis](https://github.com/cordiverse/cordis) 驱动，当前处于**开发者预览**阶段（`0.1.0-rc.5`），**存在破坏兼容性变更**。
- `dsh` 的原生入口是 `dsh web`（浏览器 Web UI，默认 `http://127.0.0.1:3080`）与 `dsh --profile headless`（无 UI 一次性运行）。
- `dsh` 已完成 **Host/Client 分层**，且 RPC 协议**与物理通道解耦**（`AbstractApiClient` + 四象限消息模型），文档中明确预留了 Electron 的 **IPC 载体**接入路径。

## 3. 目标与原则

**目标**：

- 为 `dsh` 提供一个**一等公民**的桌面应用，而非「包一层 `dsh web` 指向 localhost」的粗壳。
- 100% 复用 `dsh` 现有 Web UI，不 fork UI。

**原则**：

1. 数据面走 **IPC**，零端口、零鉴权、零 CORS（遵循 `dsh` 文档预留设计）。
2. 只写「装配代码」，不造轮子——复用 `runProfile` / `toFetchHandler` / `AbstractApiClient` 三块现成拼图。
3. 进程边界设计成**可迁移**：Host 将来可平滑迁到 `utilityProcess` 做崩溃隔离，不推倒重来。

## 4. 目标平台与分发

- **平台**：Windows + Linux（macOS 后续再考虑）。
- **分发（现阶段）**：先本地打包自用（Electron Forge `make`），暂不做自动更新、代码签名、商店分发。

## 5. MVP 功能范围

**v1 必做**：

- 系统托盘 + 后台驻留
- 原生通知
- 原生文件/目录选择器
- 无边框窗口 / 自绘标题栏
- 剪贴板图片粘贴
- 多窗口

**暂缓**：全局快捷键唤起、开机自启。

## 6. 参考实现分析

### 6.1 opencode desktop（参考子工程 `packages/desktop/`）

| 维度 | opencode 的做法 |
|---|---|
| UI 壳加载 | 自定义协议 `oc://renderer/index.html`（privileged scheme，`supportFetchAPI + stream`），**非** `file://`、**非** localhost |
| 数据面 | 渲染进程 `fetch` 直连 `http://127.0.0.1:PORT` + Basic auth（`opencode:随机UUID`），**不过 IPC** |
| 后端进程 | v1：opencode server 库打包进 `utilityProcess.fork`；v2：spawn 真实 `opencode-cli` 二进制 `service start` |
| 端口 | `127.0.0.1` 动态空闲端口 + 随机密码 |
| 就绪判定 | 两级（ready 消息 + `/api/health` 轮询），渲染进程 `await-initialization` 一个 IPC 阻塞等待 |
| IPC 职责 | 很薄：只做窗口/对话框/store/更新/深链等 OS 原生事务 |
| 安全 | `sandbox:true` + `contextIsolation:true` + `nodeIntegration:false` |
| 构建 | electron-vite + electron-builder（非 Forge） |

**关键差异**：opencode 的 RPC 天生 HTTP-first，桌面版被迫保留端口 + 鉴权 + CORS；`dsh` 的 RPC 天生通道无关，可直接走 IPC，更干净。

### 6.2 dsh 的 Electron 预留（决定性的架构事实）

- `docs/subsystems/web-server.zh.md` / `packages/host/webserver/README.md` 明示：**「Electron 通过 `file://` 加载 dist，并经 IPC 桥接承载 fetch，不使用本服务器（webserver）」**。
- `.agents/notes/implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.md` 的 `AbstractApiClient` 子类表预留了「**IPC 桥子类（假想示例——尚无此形态）Electron 壳：只需换 `doFetch`，约定/基类零改**」。
- `apps/cli/src/profile-boot.ts` 的 `runProfile({ profile }) → { ctx, shutdown }` 可在**当前进程内**挂起 Host 插件树并返回 Cordis `ctx`——这就是文档所称 `startHost()`。
- `packages/host/apiproxy` 的 `toFetchHandler(ctx.apiProxy)` 在 host 侧把 RPC 网关变成**标准 fetch handler**，且**含 SSE 下行 codec**。

## 7. 架构方案（选定：方案 A）

三个方案的核心分歧：**数据面走 IPC 还是 HTTP？Host 跑在哪？**

| 方案 | 数据面 | Host 位置 | 结论 |
|---|---|---|---|
| **A** | IPC（`IpcApiClient.doFetch`） | Electron 主进程内 `runProfile()` | **选定主线** |
| B | HTTP（localhost + Basic auth） | 子进程 spawn `dsh web` | 兜底 / 最快验证 |
| C | IPC（跨两跳） | `utilityProcess` 隔离 | 演进目标 |

**方案 A 说明**：主进程内 `runProfile('desktop')` 挂 Host（`apiProxy` + client 包图，**不挂 webserver，零端口**）；渲染进程 `file://` 加载 `apps/web` 构建产物；`IpcApiClient extends AbstractApiClient` 只覆写 `doFetch` 走 `ipcRenderer.invoke` → 主进程 → `toFetchHandler(ctx.apiProxy)`。

**选择理由**：最贴合 `dsh` 官方预留设计、实现最干净、原生集成最顺，三块拼图（`runProfile` / `toFetchHandler` / `AbstractApiClient`）均已存在，主要工作是「写装配代码」而非「造轮子」。

**诚实提醒**：方案 A 的「Harness 崩溃 = 整个应用崩溃」是真实短板（opencode 用 `utilityProcess` 隔离正为此）。因此把 Host 与主进程的边界从一开始就设计成可迁移——渲染进程只依赖 `doFetch`，Host 在 main 还是 utilityProcess 是内部实现，将来要隔离时平滑演进到方案 C。

## 8. 消费方式（默认：选项 2，待确认）

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 1. npm 依赖 | 依赖 `@deepseek-ai/dsh` + host 包 | 干净、标准、版本清晰 | 开发者预览破坏性变更；`apps/web` 前端 dist 未必以可 import 的包发布，仍需自建；包面可能不全 |
| **2. 本地源码引用** | pnpm workspace / `file:` 依赖指向 `D:\GitHub\deepseek\deepseek-harness` | 完全可控、紧跟上游、能直接 import 任意包、前端自建 | 耦合深、每次 dsh 更新需重 build、打包需处理 dsh 的 node_modules 布局（native landlock 等） |
| 3. git submodule | pin 到某个 commit | 确定性、可复现 | submodule 管理成本 |

**推荐选项 2**：dsh 开发者预览迭代快 + 方案 A 需深度 import host/client 包 + 前端 dist 必须自建，pnpm workspace 链接最顺；待 dsh 稳定发布后平滑切到选项 1。

## 9. 进程模型

```
┌─ Electron 主进程（Node.js，也承载 dsh Host）───────────────┐
│  runProfile('desktop') → ctx                                │
│    ├─ apiProxy          ← RPC 网关（createApiProxy）        │
│    ├─ client 包图        ← connection/runtime/ui-* 的 node 半边│
│    └─ 无 webserver、无端口                                   │
│  fetchHandler = toFetchHandler(ctx.apiProxy)  ← 含 SSE 下行 │
│  ┌─ ipcMain.handle('dsh:unary') / ('dsh:stream') ─────────┐ │
│  └─ Tray / Notification / dialog / 多窗口 / 原生能力       │ │
└──────────────▲─────────────────────────────────────────────┘ │
               │ contextBridge：window.dsh（doFetch 桥接）      │
┌──────────────┴───────────────────────────────────────────────┐
│ 渲染进程（每个窗口一个）：file:// 加载 apps/web dist            │
│   IpcApiClient extends AbstractApiClient                      │
│     doFetch = 经 MessageChannel 透明搬运（字节/帧）            │
│   UI 完全复用 dsh client（connection/runtime/ui-*）           │
└──────────────────────────────────────────────────────────────┘
```

## 10. 数据流：RPC 四象限 → IPC 映射

`dsh` 的 wire 协议是**通道无关的四象限消息**（`ClientRequest / ServerResponse / ServerRequest / ClientResponse`）。IPC 载体映射：

| 象限 | HTTP 载体 | IPC 载体（本工程实现） |
|---|---|---|
| ① `ClientRequest` | `POST /api/<method>` | `ipcRenderer.invoke('dsh:unary', {url, init})` 同步往返 |
| ② `ServerResponse` | 该 POST 应答体 | invoke 的返回值 |
| ③ `ServerRequest`（`session/event` 帧、审批/问答 requested） | WebSocket 下行（mux/host 两路） | `dsh:stream` 经 `MessageChannel` port 流式推送 |
| ④ `ClientResponse` | `POST /api/respond` | 同 ① 走 invoke（client-response 透传） |

**为什么「只需换 doFetch」成立**：`toFetchHandler(ctx.apiProxy)` 已把整个 `ctx.apiProxy` 变成标准 fetch handler，且**连 SSE 下行 codec 都带好了**。因此主进程侧 `doFetch` 只需把 `{url, init}` 丢给 `fetchHandler(new Request(url, init))` 并透明搬回结果——**主进程不懂协议细节**；渲染进程侧 `IpcApiClient` 只覆写 `doFetch`，unary 走 `invoke`（返回伪造 `Response`），下行帧流走 `MessageChannel` 组装成 `ReadableStream` 喂给基类 `readSse`。基类里 `readSse` / `callUnary` / `respond` / rpcId mint / zod 校验 / 微任务合批观测 **一行不改**。

## 11. 自定义 profile（默认：A1，待确认）

方案 A 需要「web 组合减去 webserver」：

- **A1：新建 `desktop` profile**（`dsh.profile.bundles = [dsh-base, dsh-web-app]` 再 patch 掉 webserver 行，或 `[dsh-base]` + 手动挂 client 包图）。干净、可演进，需自维护一份组合。**（推荐）**
- **A2：复用 `web` profile，运行时 patch 掉 webserver**（`--patch {id:'webserver', disabled:true}`）。最省事，但依赖 web profile 内部行 id 稳定性。

## 13. 六个 MVP 桌面能力 → 落地映射

| 能力 | 落地方式 |
|---|---|
| 系统托盘 + 后台驻留 | 主进程 `Tray`；关窗 = 隐藏到托盘；`window-all-closed` 不退出 |
| 原生通知 | 主进程订阅 `session/event`（`approval/requested`、`question/requested`、turn 完成）→ Electron `Notification` |
| 原生文件/目录选择器 | dsh 已预留 `host.pickDirectory` native seam（`directory-picker-native`）；桌面工程实现其 native backend，用 `dialog.showOpenDialog`；`host.openPath` 用 `shell.openPath` |
| 无边框窗口/自绘标题栏 | `BrowserWindow({ frame:false, titleBarOverlay })`；窗口控制（min/max/close）走 IPC；与 dsh web UI 视觉一体 |
| 剪贴板图片粘贴 | 渲染进程监听 paste 读剪贴板图片 → 走 dsh 图片附件路径（`session.prompt` 的 attachment）；或主进程读剪贴板经 IPC 传入 |
| 多窗口 | 主进程多 `BrowserWindow` 注册表；每窗口绑定一个 sessionId；dsh 会话路由已支持多会话，每窗口独立渲染进程 + 独立会话 |

## 14. 构建/打包 · 生命周期 · 错误处理 · 测试

- **构建打包**：Electron Forge。makers：Windows `maker-squirrel`（或 NSIS）+ Linux `maker-deb`/`maker-rpm`（或 AppImage）。打包时把 dsh host/client 构建产物 + `apps/web` dist + 自定义 profile 打进 `resources/`。
- **生命周期**：
  - 启动：单实例锁 → `runProfile('desktop')` → apiProxy 就绪 → 建窗 → `file://` 加载 dist → 渲染进程 `window.dsh.ready()` 握手。
  - 关闭：关窗 → 隐藏托盘；真正退出 → `shutdown.shutdown()` dispose 插件树 → `app.quit()`。
  - 崩溃：harness 在主进程 = 应用崩溃（方案 A 已知代价），加 `uncaughtException`/`unhandledRejection` 兜底 + 用户提示，并在 `host.ts` 边界预留 utilityProcess 迁移点。
- **错误处理**：业务错误走 dsh 的 `RpcError`（`RpcResult.error` 分支，基类已处理）；传输错误（IPC 断）由 `doFetch` 抛异常；zod 校验失败 = `bad-request`（基类已处理）。
- **测试**：单元——`IpcApiClient.doFetch` 与 dsh 的 `InProcessApiClient` 对照（同构载体测试已存在）；集成——主进程 `runProfile` + `toFetchHandler` 冒烟；e2e——后续可选。

## 附录：关键接口源码核实（2026-08-14）

对「`IpcApiClient extends AbstractApiClient`，只写 `doFetch`，基类零改」这一承重断言做了源码级核实（`packages/host/apiproxy/src/`）：

1. **`AbstractApiClient`**（`src/fetch/client.ts:244`）：`export abstract class AbstractApiClient implements IApiClient`，唯一抽象方法是
   `protected abstract doFetch(input: URL, init?: RequestInit): Promise<Response>`。
   基类持有全部协议不变量：`callUnary`（rpcId mint → tap → POST → 信封 parse → rpcId 回显校验 → 值 parse）、`readSse`（流式 fetch + `\n\n` 分帧 + `data:` 拼接）、`respond`、`postJson`、`resolveBase`、`mintRpcId`、`onEnvelope`/`subscribeEnvelopes`（微任务合批观测）。**子类只需实现 `doFetch`，结论成立。**

2. **`toFetchHandler`**（`src/fetch/handler.ts:243`）：`export function toFetchHandler(api: ApiProxy): { fetch: typeof fetch }`，把 `ctx.apiProxy` 变成纯 WHATWG `Request → Response` 函数，**自带 SSE 下行 codec**：处理 `GET /api/events.mux`、`GET /api/events.host`（SSE 帧流）、`GET/HEAD /api/session.export`（下载）、`POST /api/<method>`（unary 分派）、`POST /api/respond`（client-response）。主进程侧零协议知识，结论成立。

3. **`InProcessApiClient`**（`src/fetch/client.ts:520`）已存在：`new InProcessApiClient(toFetchHandler(api))` 全程不过网络——IPC 子类即同一模式换一个传输切面。

4. **发布状态**：`@deepseek-ai/dsh-host-apiproxy` 为 `0.1.0-rc.5`、`publishConfig.access: public`，exports 含 `.`、`./client`（→ `fetch/client.js`）、`./api`、`./src/*`。故 `AbstractApiClient` 与 `toFetchHandler` 均可 import。

**实现要点（IPC 桥的具体工作，补充到第 10 节）**：

- `doFetch` 收 `URL`、返回 WHATWG `Response`。IPC 需序列化 `Response`：
  - unary / respond：主进程 `toFetchHandler(api).fetch(...)` 后读完整 body，返回 `{ ok, status, headers, bodyText }`；渲染进程用 `new Response(bodyText, { status, headers })` 还原。
  - 流（mux / host）：`readSse` 依赖 `response.body.getReader()`，故主进程把 SSE body 逐块经 `MessageChannel` 推送，渲染进程用 `ReadableStream` 组装 `Response.body`。
- `resolveBase()`：Electron `file://` 下 `location.origin === 'null'`，返回假 authority `http://dsh.internal`——无影响，`doFetch` 只用 `input.pathname` 路由，不做真实网络。
